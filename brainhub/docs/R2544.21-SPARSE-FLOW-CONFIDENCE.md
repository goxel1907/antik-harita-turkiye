# R2544.21 Sparse-Flow Confidence Hardening

Release target: `R2544.21-SPARSE-FLOW-CONFIDENCE`

## Why this release exists

R2544.20 correctly added pre-entry adverse-selection evidence for JEV from public Binance `bookTicker`, `aggTrade`, partial depth, derivatives and observed liquidation data. Live validation on a lower-activity altcoin then exposed an important precision issue: a short window could be technically `available=true` with only a handful of Level-1 book transitions. An extreme 5-second normalized OFI from four transitions must not carry the same evidential weight as a 60-second window backed by dozens of transitions.

R2544.21 keeps the R2544.20 architecture and JEV-final authority, but makes sampling sufficiency explicit and confidence-weights the short-horizon evidence before it contributes to trap/support indices.

## Core rule

For each 5s / 15s / 30s / 60s window, confidence is deterministic:

`windowConfidence = coverageScore × sampleScore`

where:

- `coverageScore = min(1, observedCoverageMs / (0.90 × nominalWindowMs))`
- `sampleScore = min(1, observedEvents / fullConfidenceTarget)`

The confidence is an engineering sufficiency index, **not a calibrated probability**.

| Window | Full-confidence transitions |

|---|---:|

Confidence labels:

- `FULL` >= 0.80
- `MODERATE` >= 0.50
- `SPARSE` >= 0.20
- `VERY_SPARSE` > 0
- `UNAVAILABLE` = 0

## How weighting changes JEV evidence

R2544.20 base component weights are retained, but event-dependent components now use:

`effectiveWeight = baseWeight × windowConfidence`

This applies to:

- `FLOW_RESPONSE_5s/15s/30s/60s`
- `L1_OFI_RESPONSE_5s/15s/30s/60s`
- confidence-weighted multi-window flow persistence
- the 30-second queue-shift component
- the toxicity proxy, which remains explicitly **not true VPIN**

Instantaneous descriptors such as current queue imbalance or current microprice are not falsely relabeled as multi-window OFI and retain their separate semantics.

## Short-window confidence

The pre-entry packet now exposes `samplingConfidence` with:

- `shortWindow.score/quality`
- `overall.score/quality/usable`
- per-window OFI confidence
- per-window trade-flow confidence
- `sparseWindows[]`

This separates two different ideas:

1. `reliability`: is the feed fresh, connected and broadly populated?
2. `samplingConfidence`: does this specific time window contain enough temporal coverage and events to deserve its nominal weight?

A feed can therefore remain `HIGH` reliability while its 5s/15s window is correctly marked `SPARSE`.

## JEV policy

JEV remains the final strategic decision maker. R2544.21 does not create a new hard gate, probability model, named market-maker detector or execution authority.

The JEV prompt explicitly instructs:

- never treat sparse windows as equal to well-sampled windows;
- prefer better-sampled 30s/60s evidence when short-window evidence conflicts;
- never allow low-reliability/warming evidence to veto a sound setup by itself;
- use the layer to improve `MARKET_NOW` versus `WAIT_*` timing, not to replace the 5m/15m thesis.

## Learning / case memory

New immutable cases are versioned `R2544.21` and preserve the compact sampling-confidence state. Older R2544.20 and R2544.19 immutable cases remain readable with explicit fidelity labels. Winners and losers are still retrieved together; no single trade becomes an automatic rule.

## Validation target

The regression suite includes a PROM-like sparse case with 4 OFI transitions in ~3.6s, 7 in ~14.1s, 23 in ~28.8s and 73 in ~59.2s. The expected result is that 5s/15s are marked sparse and down-weighted while the 60s window can still achieve full sampling confidence.
